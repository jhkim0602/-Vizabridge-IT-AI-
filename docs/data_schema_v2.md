# 검수용 CSV v2 스키마

- 버전: **v2**
- 기준일: **2026-05-18**
- Single source of truth: [`scripts/schema.py`](../scripts/schema.py)
- 적용 산출물: `data/processed/체류매뉴얼_검수용.csv`, `data/processed/사증매뉴얼_검수용.csv` (파일명 규칙은 §6 참고)

본 문서는 사람 검수와 Notion 임포트, 후속 RAG/챗봇 CSV 변환에서 모두 동일한 기준으로 사용할 검수용 CSV의 컬럼·Enum·빈 셀·인코딩 규약을 정의한다. 빌더 스크립트(`scripts/build_*`), 정규화 스킬(`.claude/skills/vizabridge-*`), Notion 변환기(`scripts/notion_*`)가 한 곳에서 컬럼 정의를 import 할 수 있도록 모든 컬럼명·Enum 값은 `scripts/schema.py` 의 상수로 고정한다.

---

## 1. 문서 목적

v1 (`docs/data_columns.md`) 의 영문 컬럼 25+개 스키마는 LLM 풍부화와 RAG 친화 컬럼이 섞여서 **사람 검수자에게는 너무 많고, JSON 변환·Notion 임포트 때 컬럼이 또 달라지는** 문제가 있었다. 클라이언트 피드백을 종합하면 다음 3가지를 동시에 만족해야 한다.

1. **빈 셀 보존** — 정보가 없는 항목은 빈 셀이어야 한다. `"-"`, `"내용없음"`, `"없음"` 처럼 사람이 만든 빈 값 표기는 후속 단계에서 모두 다른 의미로 오해된다.
2. **누락 ZERO** — 매뉴얼에 분명히 적힌 행정 항목(점수표·쿼터·초청자·추천기관 등)이 자유 텍스트 셀에만 묻혀서는 안 된다. 전용 컬럼을 둬서 누락 여부가 한 눈에 보이게 한다.
3. **JSON/RAG/Notion 변환 시 기준 일치** — 같은 컬럼명·같은 Enum 사전·같은 빈 셀 표기를 유지해야 후속 변환에서 매핑 비용이 0 이다.

v2 는 32컬럼으로 컬럼을 늘리는 대신, **컬럼별로 명확한 의미와 빈 셀 정책**을 부여해서 위 세 요건을 동시에 만족시킨다.

## 2. 한 행의 단위 — (비자코드 × 신청종류)

### 결정

한 행 = **(비자코드, 신청종류)** 조합 1건.

- 예: F-6-1 (결혼이민) 은 다음과 같이 최대 5행으로 펼쳐진다.
  - F-6-1 × 사증발급
  - F-6-1 × 체류자격 변경
  - F-6-1 × 체류기간 연장
  - F-6-1 × 외국인등록
  - F-6-1 × 재입국허가

### 왜 "한 비자 = 한 행" 이 아닌가

한 비자코드당 한 행으로 묶으면 "행정 내용" 자유 텍스트 셀에 사증발급 / 체류자격 변경 / 기간 연장의 자격요건·서류·절차가 전부 들어가서 **셀당 5,000자**가 흔하게 발생한다. 영향:

- Google Sheets / Notion 임포트 시 셀 잘림.
- 사람 검수자가 하나의 셀에서 "지금 보는 건 사증발급 기준인가 변경 기준인가" 를 매번 추적해야 한다 — 검수 속도가 떨어지고 오해가 발생한다.
- RAG 청크는 보통 "한 행 → 한 청크" 매핑인데, 한 행이 너무 크면 청크 분할이 다시 필요하다.

신청종류로 행을 펼치면 셀당 평균 길이가 200~800자 수준으로 떨어지고, 검수·임포트·RAG 어느 쪽에서도 의미 경계가 명확해진다.

### 단점과 보완

- 같은 행정 내용이 두 신청종류에 공통일 때 텍스트 중복이 생긴다 → `공통사항` 컬럼에 한 번만 쓰고, 행 단위에서는 비워둘 수 있다. 또는 두 행 모두에 동일 텍스트를 채워서 검수자가 한 행만 보고 의사결정할 수 있게 한다 (정규화 스킬이 선택).
- 한 비자코드가 신청종류 1개만 가지면 행이 1개로 끝난다 — 펼침 비용은 없다.

### `MANUAL_KIND` — 2종

```

```

### `PETITION_TYPES` — 11종 (Phase 2 audit 결과로 보강 가능)

- `사증발급`
- `사증발급인정서`

- `체류자격 변경`

- `체류기간 연장`
- `외국인등록`

- `공통사항`

## 5. 빈 셀 정책

| 입력 값 | 정규화 결과 |
|---|---|
| `""` | `""` (그대로) |
| `None` | `""` |
| `"-"` | `""` |
| `"없음"`, `"내용없음"`, `"해당없음"` | `""` |
| `"NaN"`, `"null"`, `"N/A"` (대소문자 무시) | `""` |
| 위 외의 모든 값 | `str()` 캐스팅 그대로 |

규칙:

- 빈 셀은 빈 문자열 `""` 로 통일한다.
- 의미 있는 값으로 보이지 않는 한국어 표현(`없음` / `내용없음` / `해당없음`) 도 빈 셀로 정규화한다 — 후속 단계에서 "값이 있긴 한데 비어있다고 적힘" 으로 오해될 위험을 차단한다.
- **다만 `0`, `면제`, `해당` 같이 정보가 있는 값은 그대로 둔다.** 예: 수수료 `"면제"` 는 정보, `"없음"` 은 모름.
- 빈 셀 정규화는 `scripts/schema.py` 의 `normalize_blank()` 가 단일 진입점이다.

`scripts/schema.py` 의 `validate_row()` 는 위 정규화를 자동 수행한 뒤 enum 검증을 한다. 빌더는 validate_row 의 반환값을 그대로 CSV 에 써야 한다.

## 6. 인코딩·파일명 규칙

### 인코딩

- CSV 파일: **utf-8-sig** (BOM 포함). Excel/Google Sheets 한국어 호환을 위함.
- 줄바꿈: `\n` (LF). Windows 호환은 reader 책임.
- newline 분리 필드(`예상질문`, `제출서류`) 는 셀 안에서 `\n` 그대로 두고, CSV 인코더가 `"..."` 로 quote 한다.

### 파일명

검수용 CSV:

- `data/processed/체류매뉴얼_검수용.csv`
- `data/processed/사증매뉴얼_검수용.csv`

Notion 임포트용 (검수용 CSV 의 부분집합 또는 가공판):

- `data/processed/체류매뉴얼_노션검수용.csv`
- `data/processed/사증매뉴얼_노션검수용.csv`

배치 산출물:

- `output/notion_batches/{stay,visa}_batch_NN.json` — 한 페이지 = 한 행. 100페이지/배치 미만.

## 8. 클라이언트 피드백과 컬럼의 매핑

| 피드백 | 해결 위치 | 동작 |
|---|---|---|
| "빈 셀이 보존되어야 합니다." | §5 빈 셀 정책, `normalize_blank()` | `"-"` / `"없음"` 자동 정규화. |
| "점수표·쿼터 같은 항목이 자유 텍스트에 묻혀 누락된다." | `점수표`(17), `쿼터`(18) 전용 컬럼 | 전용 컬럼이 비어있으면 누락 가능성으로 한 눈에 보임. |
| "초청자/추천기관이 사증 매뉴얼에서 누락된다." | `초청자`(19), `추천·승인기관`(20) | 사증 매뉴얼 측 누락 ZERO 보장. |
| "한 비자에 모든 행정 내용이 한 셀에 들어가 검수가 어렵다." | §2 행 단위를 (비자코드 × 신청종류) 로 분해 | 셀당 평균 길이 감소. |
| "원본 어디 줄에서 왔는지 검증할 수 없다." | `섹션`(24), `페이지`(25), `원본 라인범위`(26), `원문발췌`(29) | 출처 4컬럼으로 GitHub 점프 + LLM 환각 교차검증. |
| "RAG/챗봇 변환 때 컬럼이 또 달라진다." | `scripts/schema.py` 단일 진입점 | 모든 downstream 변환기가 본 모듈 import. |
| "검수 진행 상황을 추적하고 싶다." | `검수상태`(31), `검수메모`(32) | Notion DB 에서 상태 필터링 가능. |
| "비자 코드 모르는 사용자도 검색할 수 있어야." | `키워드`(28), `예상질문`(30), `연계비자`(27) | 사용자 자연어 → 검색 가중. |
| "신청종류별로 절차·서류가 다르다는 걸 명확히 봐야." | §2 행 단위 + `신청종류`(4) enum | 한 행 = 한 신청종류. |

## 9. 마이그레이션 노트 (v1 → v2)

- v1 영문 컬럼 (`manual_type`, `item_type`, `subsection_type`, …) 은 RAG 친화형 semantic CSV 의 컬럼이고, **본 v2 는 사람 검수 + Notion + 후속 변환의 공통 기반**이다. 두 스키마는 별도로 공존한다.
- v1 의 자유 텍스트 `normalized_text` 가 가지고 있던 정보는 v2 에서 `자격요건`, `절차`, `참고사항` 등으로 분해된다.
- v1 의 `score_criteria` ↔ v2 의 `점수표`, v1 의 `quota_or_limit` ↔ v2 의 `쿼터` 같이 1:1 매핑되는 컬럼은 빌더가 자동 변환 가능.
- 후속 RAG 입력 CSV 는 v2 검수용 CSV 를 입력으로 다시 만든다. 검수 단계에서 사람이 갱신한 셀이 그대로 RAG 로 흘러간다.

## 10. 변경 절차

본 스키마를 변경할 때는 다음 순서를 지킨다.

1. `scripts/schema.py` 의 `COLUMNS` / Enum 상수 수정.
2. 본 문서 (`docs/data_schema_v2.md`) 동일 위치 동기화.
3. `.venv/bin/python -c "import scripts.schema"` 로 import 검증.
4. 빌더·정규화 스킬·Notion 변환기에서 새 컬럼/Enum 이 사용 가능한지 확인.
5. 산출 CSV 를 1행 이상 `validate_row()` 로 통과시키는 sanity 테스트 추가.

스키마는 한 곳(`scripts/schema.py`) 에서만 결정한다. 본 문서는 그 결정의 사람 친화 해설이다.
