# Pipeline Strategy

## Why HWP + kordoc + Claude Code skill?

세 가지 큰 결정이 이 프로젝트의 형태를 정합니다.

### 1. PDF가 아니라 HWP를 원본으로

기존 파이프라인은 PDF를 LlamaParse OCR로 파싱했습니다. 결과적으로:

- 한글이 일부 깨지거나 인식 오류 (`E - 7`처럼 공백이 끼는 등)
- 표 구조가 자주 망가져서 첨부서류 목록이나 점수표가 깨졌습니다
- 같은 매뉴얼을 다시 파싱할 때마다 OCR 변동성이 있었습니다

이 매뉴얼들은 정부가 **HWP로 작성한 원본**이 존재합니다. 그렇다면 PDF로 출력된 사본을 OCR로 다시 인식할 이유가 없습니다.

[kordoc](https://github.com/chrisryugj/kordoc)은 HWP/HWPX/HWPML을 직접 Markdown으로 변환하는 Node.js 도구입니다. 표는 HTML `<table>` 블록으로, 중첩 셀과 병합 셀까지 보존됩니다. LibreOffice 같은 외부 컨버터 없이 자체완결됩니다.

### 2. LLM 단계와 결정적 단계의 명확한 분리

LLM이 한 번에 "Markdown 보고 CSV 행 만들기"를 다 하면:

- 출력 형식 변경마다 LLM을 다시 돌려야 함
- 할루시네이션을 한꺼번에 잡아야 해서 디버깅이 어려움
- 캐싱/재실행 단위가 통째라서 비싸짐

그래서 **중간 표현(canonical intermediate representation)**으로 정규화 Markdown을 둡니다. 컴파일러의 IR과 동일한 아이디어입니다.

```
원본 → [LLM 정규화] → 정규화 MD → [결정적 빌드] → CSV
                            ↑
                    여기서 사람도/Python도 검수 가능
```

이 분리의 효과:

| 효과 | 이유 |
| --- | --- |
| 검증 가능성 ↑ | 정규화 MD를 원본과 결정적으로 교차 검증 (validator) |
| 재현성 ↑ | 정규화 MD를 git에 커밋. 같은 입력 → 같은 CSV |
| 디버깅 분리 | "LLM이 틀림" vs "CSV 빌더가 틀림" 구분 가능 |
| 스키마 변경 비용 ↓ | CSV 컬럼 추가/제거는 빌더만 수정. LLM 재실행 불필요 |
| 사람 검수 용이 | 정규화 MD가 YAML-스러운 한 청크 블록 → 읽기 쉬움 |

### 3. Claude Code 스킬 (API 결제 회피)

LLM 단계를 별도 Anthropic API 호출로 만들면 결제가 별도로 발생합니다. 이 프로젝트는 Claude Code Max 구독으로만 운영하므로, LLM 작업을 **Claude Code 스킬**로 만들었습니다.

스킬 (`.claude/skills/vizabridge-*`)은 사용자가 `/vizabridge-normalize` 같은 슬래시 명령으로 호출하면, Claude Code 세션 안의 모델이 그 지침을 따라 작업합니다. 결제 단위는 Max 구독, 동일한 Claude 모델, 단지 호출 경로만 다릅니다.

트레이드오프:

- 장점: 추가 결제 0원, 같은 모델 품질
- 단점: 자동화 아님 (사람이 명령 입력), CI 미지원
- 보완: 정규화 MD를 커밋해서 재현성 확보 — CSV는 결정적 Python으로 언제든 재생성

## How chunking works

kordoc 출력의 가장 안정적인 구조 단위는 **top-level `<table>` 블록**입니다. 사증/체류 매뉴얼 모두 비자코드 섹션이 `<table>` 단위로 정리됩니다.

다만 다음 엣지케이스가 있어서, 처음 시도한 "한 비자코드 = 한 청크" 접근은 깨졌습니다:

- 체류 매뉴얼의 F-2 헤더가 `<th>.</th>` (점 하나)로 깨져 있음
- 양 매뉴얼의 H-2가 보조 표에만 등장하고 메인 비자코드 헤더 자리에는 없음
- F-4 재외동포는 본문 + 38번 부록에 두 번 등장
- E-7은 본 표 하나 + 후속 sub-table 수십 개 (E-7-1 ~ E-7-S)로 4000+ 줄 차지

그래서 청크 전략은:

1. top-level `<table>` 경계로만 절단
2. 누적 크기가 ~15K chars 달하면 다음 표 직후에 끊음
3. 각 청크에 그 내용 안에서 발견되는 모든 비자코드(regex)를 메타데이터로 부착
4. 한 청크가 여러 비자코드를 다룰 수 있다 (예: 부록 chunk_017에 F-2/F-5/D-8/A-1 다 등장)

정규화 스킬이 청크당 N개 행을 만들 때 비자코드는 1:1이 아니라 N:M 관계로 다룹니다. 이 단순한 가정이 모든 엣지케이스를 자연스럽게 흡수합니다.

## Korean Administration Manual Structure

매뉴얼 본문은 다음 반복 구조입니다.

- 표지, 목차, 유의사항, 공통사항 (결핵진단서 등)
- 체류자격별 장 (외교 A-1, 기업투자 D-8, 특정활동 E-7, …)
- 각 장 내부 반복 블록: 활동범위, 해당자, 자격요건, 관리기준, 체류기간 상한, 발급대상, 첨부서류, 비고
- 붙임/서식/FAQ/점수표
- 주의 문구: "심사를 위해 필요한 경우 서류를 가감할 수 있음" 같은 공통 제한사항

최종 CSV의 행 단위는 페이지가 아니라 다음 계층입니다:

1. 매뉴얼 유형: 사증민원 또는 체류민원
2. 체류자격/비자 코드: D-8, E-7, F-6 …
3. 민원 유형: 사증발급, 사증발급인정서, 체류자격 변경, 기간연장, 근무처 변경 …
4. 하위 항목: 대상, 요건, 서류, 제한, 절차, FAQ
5. (챗봇 CSV에 한해) 사용자 의도 태그: 결혼/배우자, 유학/연수, 취업/고용 …

## Final CSV Design Principle (v4)

본 데이터셋은 「매뉴얼 원문이 ground truth」 원칙에 따라 임의의 요약·가공 없이 매뉴얼 원문 표현을 보존합니다. 임베딩·검색·챗봇 응답과 같은 후속 가공은 별도 단계에서 본 데이터셋을 입력으로 받아 수행하는 것을 전제로 합니다 (보고서 Abstract / 6.2).

산출물은 1종 — `{사증,체류}매뉴얼_최종_v4_26col.csv/.xlsx`. 한 행 = `(비자코드 × 신청종류)` 1조합. 26컬럼은 보고서 2.1 「26 컬럼 한눈에」 카테고리 6 분류를 따릅니다.

CSV에는 raw text, review/debug 컬럼을 넣지 않습니다. 원문 페이지 출처는 `출처` 컬럼에 `(p. NNN)` 형식으로 통합되어 검수자가 PDF 페이지로 즉시 점프할 수 있습니다. 검수 워크플로용 컬럼(`검수상태`, `검수메모`)은 본 데이터 계층에 포함하지 않고, Notion import 후 별도 컬럼을 추가하는 방식으로 운영합니다.

## What changed vs the legacy pipeline

| | 과거 (LlamaParse 기반) | 현재 (v4) |
| --- | --- | --- |
| 원본 | PDF (OCR) | HWP (정확) |
| 1차 도구 | LlamaParse API ($) | kordoc CLI (무료, 로컬) |
| 의미 분류 | 999줄 정규식 | Claude Code 스킬 (`/vizabridge-normalize`) |
| 할루시네이션 방지 | 없음 (규칙 기반이라 불필요) | `scripts/validate_normalization.py` (결정적 cross-validation) |
| 재실행 비용 | 정규식 다시 돌리기, OCR 변동성 | 0 (정규화 MD 커밋되어 있음) |
| API 결제 | LlamaCloud $$ | 0 (Max 구독으로 흡수) |
| 산출물 | semantic + chatbot 2 CSV (스키마 가변) | v4 26컬럼 CSV/XLSX 1종 (사증 158 / 체류 275) |

레거시 정규식 빌더와 옛 챗봇 풍부화 단계는 본 저장소에서 제거되었습니다 — 보고서 1차 전처리 결과만 ground truth 로 유지하고, 임베딩·검색·챗봇 응답 등 후속 단계는 본 데이터셋을 입력으로 받는 별도 단계로 분리합니다 (보고서 6.2 참조).
