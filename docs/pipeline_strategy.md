# Visa RAG Pipeline Strategy

## Parse First or Split First?

결론부터 말하면, 이 프로젝트에서는 **LlamaParse로 먼저 샘플 파싱하고, 그 결과를 보고 나중에 섹션/청크 단위로 나누는 방식**이 맞습니다.

다만 처음부터 PDF 전체를 바로 파싱하지는 않습니다. 먼저 대표 구간을 샘플 파싱해서 제목, 표, 페이지, 비자코드가 어떻게 추출되는지 확인한 뒤 전체 파싱으로 넘어갑니다.

현재 원본 파일 기준 페이지 수는 다음과 같습니다.

| PDF | PDF Pages | Layout Note |
| --- | ---: | --- |
| 사증민원 자격별 안내 매뉴얼 | 482 | 세로 A4, 자격별 반복 표 구조 |
| 체류민원 자격별 안내 매뉴얼 | 383 | 가로 A4, 일부 구간은 두 쪽이 한 PDF 페이지처럼 배치됨 |

사용자가 말한 것처럼 업무량은 대규모입니다. 두 파일을 합치면 865 PDF 페이지이고, 체류민원은 한 PDF 페이지 안에 문서상 두 쪽이 보이는 구간이 있어 실제 정보량은 페이지 수보다 더 큽니다.

## Korean Administration Manual Structure

한국 행정 매뉴얼은 일반 책처럼 자연어 문단이 이어지는 형태가 아니라, 다음 구조가 반복됩니다.

- 표지, 목차, 유의사항, 공통사항
- 체류자격별 장: 외교(A-1), 기업투자(D-8), 특정활동(E-7) 등
- 각 장 내부의 반복 블록: 활동범위, 해당자, 자격요건, 관리기준, 체류기간 상한, 발급대상, 첨부서류, 비고
- 붙임/서식/FAQ/점수표: 표와 문답이 많고, 실제 상담 질문과 직접 연결되는 경우가 많음
- 주의 문구: "심사를 위해 필요한 경우 서류를 가감할 수 있음" 같은 공통 제한사항

따라서 RAG 데이터는 단순히 `페이지 단위`로 나누면 안 됩니다. 최종 단위는 대략 다음 계층을 따라야 합니다.

1. 매뉴얼 유형: 사증민원 또는 체류민원
2. 체류자격/비자 코드: D-8, E-7, F-6 등
3. 민원 유형: 사증발급, 사증발급인정서, 체류자격 변경, 기간연장, 근무처 변경 등
4. 하위 항목: 대상, 요건, 서류, 제한, 절차, FAQ
5. 사용자 의도: 퇴사, 이직, 법인설립, 가족초청, 유학 후 취업, 연장, 벌금/체납 등

## Why Parse First?

원본 PDF를 먼저 임의로 자르면 다음 문제가 생깁니다.

- 표가 페이지 경계에서 잘리면 필요서류 목록이 깨질 수 있습니다.
- 비자코드 제목과 실제 설명이 다른 조각으로 분리될 수 있습니다.
- 페이지 번호만 기준으로 자르면 고객 질문 의도와 연결될 섹션 구조를 잃기 쉽습니다.
- 같은 PDF를 여러 번 업로드/파싱하게 되어 비용과 관리 복잡도가 늘어납니다.

LlamaParse는 PDF의 레이아웃, 표, 페이지, 마크다운 구조를 추출하는 도구입니다. 따라서 먼저 문서 구조를 보존한 Markdown/JSON을 만들고, 그 다음 RAG 목적에 맞게 섹션을 나누는 편이 더 안전합니다.

## What Does "Split" Mean Here?

주의할 점은 LlamaParse 공식 문서의 `Split API`와 RAG에서 말하는 `chunking/splitting`은 목적이 다릅니다.

- LlamaParse Split API: 여러 문서가 하나의 PDF에 섞여 있을 때 문서 단위로 분리하는 기능
- 우리 프로젝트의 split/chunking: 파싱된 매뉴얼을 비자코드, 민원 유형, 고객 의도, 필요서류, 절차 단위로 나누는 작업

현재 원본 PDF는 이미 `사증민원`과 `체류민원` 두 파일로 분리되어 있으므로, LlamaParse Split API를 먼저 쓸 필요는 낮습니다.

## Recommended Order

1. API 키 확인
2. PDF 목록과 파일 크기 확인
3. LlamaParse 샘플 파싱: 목차, 공통사항, 일반 자격 장, 표/FAQ가 많은 구간을 함께 테스트
4. 샘플 Markdown/JSON 품질 확인
5. 전체 PDF 파싱
6. 파싱 결과에서 PDF 페이지 번호와 문서 인쇄 쪽번호를 분리
7. 자격별 큰 장을 먼저 분리
8. 각 장 안에서 민원 유형과 하위 항목으로 다시 분리
9. 비자코드/비자명/민원유형/고객의도/필요서류/절차 컬럼 설계
10. CSV 생성
11. 임베딩 테스트
12. 실제 고객 질문으로 검색 품질 평가

## Sampling Strategy

샘플 파싱은 앞 5페이지만으로 부족합니다. 대형 행정 매뉴얼에서는 초반 목차는 잘 나오더라도, 중간의 표/붙임/FAQ가 깨질 수 있습니다.

권장 샘플 범위:

| Manual | Suggested PDF Page Ranges | Why |
| --- | --- | --- |
| 사증민원 | `1-12,150-155,300-306` | 표지/목차/공통사항, 일반 자격 장, 중후반 서류/표 구조 확인 |
| 체류민원 | `1-15,150-155,299-306` | 가로/2단 배치, 일반 자격 장, FAQ/점수표/붙임 구조 확인 |

샘플 결과에서 다음을 확인한 뒤 전체 파싱합니다.

- 표가 Markdown table 또는 읽을 수 있는 목록으로 보존되는가?
- 비자코드와 비자명이 제목으로 살아 있는가?
- `첨부서류`, `대상`, `요건`, `제외대상`, `FAQ` 같은 하위 제목이 살아 있는가?
- 체류민원 가로 페이지의 좌우 두 쪽 순서가 뒤섞이지 않는가?
- 근거 표시용으로 PDF 페이지와 인쇄 쪽번호를 추적할 수 있는가?

## RAG Design Principle

고객은 보통 비자코드를 모릅니다. 따라서 최종 CSV는 `visa_code`만으로 검색되면 안 됩니다.

예를 들어 `D-8`이라는 코드보다 다음 표현이 더 중요합니다.

- 한국에서 법인을 설립하고 싶어요
- 외국인이 한국에서 사업하려면 어떤 비자가 필요한가요
- 투자자로 한국에 체류하고 싶어요

그래서 최종 데이터에는 원문 근거와 함께 `user_intent`, `applicant_context`, `question_examples`, `normalized_text`를 넣어야 합니다.

## Evidence Tracking

최종 답변에서 "근거가 어디냐"를 보여주려면 아래 둘을 분리해 저장해야 합니다.

- `pdf_page`: PDF 파일에서의 실제 페이지 번호
- `printed_page_label`: 문서 안에 인쇄된 쪽번호, 예: `- 151 -`

특히 체류민원 매뉴얼은 가로 A4 형식으로 두 쪽이 한 화면에 보이는 구간이 있어, PDF 페이지 번호만으로는 사용자가 원문을 찾기 어려울 수 있습니다.
